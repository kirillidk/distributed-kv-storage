# Local component logs

Enable file logging on a node with `nodes[].repl.log_dir`:

```yaml
nodes:
  - id: node-1
    repl:
      listen_addr: 0.0.0.0:7001
      connect_addr: node-1:7001
      log_dir: ./logs/node-1
    engine:
      connect_addr: 127.0.0.1:8001
      command: [./bin/kv-engine, --port, "8001"]
      restart_delay: 3s
      shutdown_timeout: 5s
```

The directory contains two append-only JSON Lines files:

- `repl.log`: supervisor startup, health changes, process exits, restarts,
  shutdown, and other events generated by `repl`.
- `kv-engine.log`: the child's stdout and stderr, with a timestamp, `stream`,
  and `line` for each observed line.

```json
{"time":"2026-10-20T12:00:00Z","level":"INFO","msg":"engine output","stream":"stderr","line":"state -> SERVING"}
```

Both components still write to the existing console output. Engine output goes
into `kv-engine.log` without also duplicating it in `repl.log`. Ordering between
stdout and stderr is the order observed by `repl`; it cannot reconstruct the
original order of writes to two separate streams. Lines longer than 64 KiB
are split into chunks, and a final line without a newline is flushed when the
child process exits.

Files are opened before the engine starts and are appended to after either
process restarts. They remain readable while the engine is down. Messages
about invalid CLI arguments or an unreadable manifest go to stderr: the log
directory is only known after a local node has been selected successfully.

If the directory cannot be opened, `repl` fails before starting the engine.
A write failure while running causes `repl` to shut down the child and return
an error. Writes are synchronous; there is no userspace queue that discards
lines. These are diagnostic files, independent of the replication WAL. There
is no per-line `fsync` or guarantee against power-loss of the newest records.

## Read API

[`ReplAdminService.ReadLogs`](../api/proto/repl/v1/admin.proto) is served on the
node's `repl.listen_addr`. Consumers such as `clusterstat` connect using
`repl.connect_addr`; they do not need access to the node's filesystem.

```json
{"component":"LOG_COMPONENT_KV_ENGINE","offset":"0","max_bytes":65536}
```

- Select `LOG_COMPONENT_REPL` or `LOG_COMPONENT_KV_ENGINE`.
- `offset` is a byte position in the selected diagnostic file, independent
  of WAL offsets. Use `0` to read the entire history from its beginning.
- `max_bytes` defaults to 64 KiB and must not exceed 1 MiB.
- Append `data` from successive responses, then pass `next_offset` as the
  next request's offset. Protobuf JSON represents `bytes data` as base64.
- A page may split a JSON record or UTF-8 character. Buffer unfinished records
  until the following page before parsing them.
- `eof` describes the file at the time of the read. Poll at the same
  `next_offset` to get bytes appended later; there is no streaming RPC.

Unrecognized components or oversized pages return `InvalidArgument`. An offset
past EOF returns `OutOfRange`. When `log_dir` is omitted, the RPC returns
`FailedPrecondition`. File read failures return `Internal`.

The files are not rotated or truncated automatically, so offsets remain valid
across restarts while the files are retained. Retention and rotation are a
separate feature; this version keeps history from the beginning. Logs are
served only by the running `repl` that owns them.

## Docker example

The single-node example stores the files under
`/var/log/distributed-kv/node-1` in the `node-logs` named volume. A normal
`docker compose down` or `up --force-recreate` preserves it. `down --volumes`
removes the volume and its history.

```bash
docker compose -f examples/single-node/compose.yaml \
  exec node-1 tail -f /var/log/distributed-kv/node-1/repl.log
```

```bash
docker compose -f examples/single-node/compose.yaml \
  exec node-1 tail -f /var/log/distributed-kv/node-1/kv-engine.log
```

Connecting the `clusterstat` UI to this API is a separate change.
